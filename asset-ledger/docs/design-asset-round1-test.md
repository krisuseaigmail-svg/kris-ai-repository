## 2. 空间父子矩阵：可实现性与边界

矩阵本身是有限、无环的允许表，服务端可硬编码。根只允许机房/仓库/办公区；机柜只挂机房；柜子只挂仓库或办公区；工位只挂办公区；办公区可挂办公区。拒绝提示六句按子类型页面用词，可测。

### 2.1 空父（根）

| 用例 | 按矩阵应得 | 设计是否写死 |
| --- | --- | --- |
| 根创建机房、仓库、办公区 | 保存 | 有。验收 1 |
| 根创建机柜、柜子、工位 | 拒绝，不产生行 | 有。验收 1，提示「这里不能放…」 |
| 把已有机柜的父级改成空 | 拒绝，父级不变 | 矩阵不含机柜-根。验收 6 只举例「机柜移到仓库」，**缺「机柜改到根」** |
| 把办公区从某办公区下改回根 | 允许 | 矩阵允许。无验收句 |
| 两个根机房名称仅大小写不同 | 拒绝「同级已有这个名称」 | 有。草案 §4.1「根节点之间也按同级比较」；设计 §11 用 `parent_id IS NULL` 部分唯一索引，这条必须保留，普通唯一约束在 PostgreSQL 里挡不住多个 NULL |

### 2.2 环

| 用例 | 按设计应得 | 是否可验收 |
| --- | --- | --- |
| 父级设为自己 | 「不能放到自己的下级」，父级不变 | 验收 6 写了子孙，**没写自己**。草案 §4.1 正文有「不是自己或自己的子孙」，验收句漏了自己 |
| 父级设为直接子节点 | 同上 | 有。验收 6 |
| 父级设为孙节点 | 同上 | 有 |
| A←B←C 后把 C 移到 A 下 | 允许（不是移到子孙，是移到祖先） | 未写。应允许，并重算整棵深度 |
| 跨类型环（机房父级改成其下机柜） | 机房只允许根，应先被矩阵拒绝 | 提示可能是「这里不能放机房」而非防环句。未规定两种都触发时用哪一句。检查顺序第 4 步把矩阵和防环捆在一起，**未规定先后** |

### 2.3 类型改

创建后类型不变，提交别的类型提示「类型创建后不能改」，原类型还在：验收 6 有。  
未写：提交**相同**类型应视为未改、可以改名称/父级。实现若把「类型字段出现在 POST 里」一律拒绝，编辑表单会废。第 2 轮必须写「仅当新类型与库中不同时拒绝」。

机柜高度随类型走：非机柜高度必须空。类型不能改，所以不会出现「机房改机柜补高度」。仍要挡：给仓库 POST 一个高度，应拒绝或忽略。未写。

### 2.4 超层

规则：从根到自身含自身最多 4。验收 4：三层办公区 + 工位可保存；已是 4 的节点下再创建提示「空间层级过深」。

设计 §5 有一句「再在最深的办公区下增加一层则不行」，和上一句「办公区/办公区/办公区/工位可以保存」打架：最深办公区是第 3 层，其下加工位恰好是合法的第 4 层。以草案验收 4 为准，设计那句作废。

**移动整棵子树未定义，这是本矩阵最大实现漏洞。**

草案 §4.1：「修改父级时……路径长度仍不超过 4」。只说被移动节点。反例：

- 根 `办公A` / `办公B` / `办公C` / `工位D`（D 深度 4）
- 另有根 `办公E`
- 把 `办公A` 移到 `办公E` 下：A 新深度 2，若只检查 A 则通过；此时 D 深度变成 5，超过上限

创建路径挡得住，移动路径挡不住，4 层不变量不成立。必须改为：移动后，该节点及其**全部子孙**的新深度都 ≤ 4，否则拒绝，提示仍用「空间层级过深」，父级不变。

其它应写进验收的超层边界：

- 四层办公区（无工位）合法；其下再加工位或办公区非法
- 机房/机柜、仓库/柜子只有两层，深度上限挤不到它们
- 深度 3 的办公区下创建柜子：柜子深度 4，合法；柜子不能再有子空间，与深度叠加

### 2.5 矩阵缺口（相对用户「逐层递进」）

- 机房下不能建柜子：机房内备件柜没有合法父级。设计 §13 已点名。相对用户把「机房、柜子」并列且要求递进，这是**部分覆盖**，不是实现做不到。
- 仓库不能套仓库、机房不能套机房：园区/楼/机房/机柜这种五层会被深度和类型双重拦住。
- 柜子不能套柜子、工位不能挂在柜子下。
- 工位不能做根：必须先有办公区。与「逐层」一致，但和「直接建一个工位」的口头理解不同。保留需在页面空态写明。

裁决：矩阵可实现，但必须补「自己」「子树深度」「同类型再提交」。机房备件柜是产品取舍，第 2 轮要在必须改里给一句终裁，不要再丢给实现。

## 3. 资产挂载边界

宿主表可实现：网络设备 = 机柜(连续 U) / 仓库节点 / 根为仓库的柜子；硬盘 = 服务器 / 仓库 / 任意柜子 / 办公区 / 工位。每条资产恰好一个宿主。机房节点不放资产。

### 3.1 硬盘进机柜

拒绝，「硬盘不能放在这里」，不产生行。验收 9 有。  
连带：硬盘进机房、硬盘挂交换机/防火墙/另一块硬盘 → 「硬盘不能放在这里」或「挂载目标不是服务器」。验收 9 有后半。硬盘进机房无独立验收句，应按同一句拒绝。

### 3.2 服务器进办公区

拒绝，「服务器不能放在这里」。验收 8 覆盖办公区、工位、根为办公区的柜子、机房节点。交换机/防火墙同句型。  
符合原文「服务器可能在机柜或仓库」，没有说进办公区。

### 3.3 U 重叠

闭区间 `[起始U, 起始U+占用高度-1]`，与机柜 1..高度 求包含，与同柜其它资产求相交。验收 10、11 有相交、超出、缺填、非机柜带 U、缩柜。

缺了这些，不写实现会各写各的：

| 用例 | 应得 | 现状 |
| --- | --- | --- |
| `[1,2]` 与 `[3,4]` 相邻 | 保存 | 未写。闭区间不相交，应允许 |
| `[1,2]` 与 `[2,3]` 端点重合 | 「U 位重叠」 | 未单独写。按闭区间必须拒绝 |
| 编辑自己、U 不变 | 保存 | 有「排除正在保存的这一条」 |
| 占用高度 0、负数、非整数 | 拒绝 | 「至少为 1」无提示原文；易和「请填写占用高度」混 |
| 起始 U 0 | 「U 位超出机柜」或格式错误 | 未写 |
| 预填占用高度 2，用户不改直接提交 | 应写入 2 | 设计 §6「缺省提交时拒绝」和草案 §5.2「清空后提交才拒绝」不一致。以草案为准，设计那句必须改 |
| 并发两台设备抢同一 U | 后提交者重叠拒绝 | 只有应用层检查，无 `EXCLUDE`/`gist` 约束。验收未要求锁。中风险，见 §6 |

机柜详情 U 表从高到低、跨 U 每行重复同一编号：可实现，只读，上架走表单。与交付台账「从下到上 + 拖拽」不同，不是本产品缺陷。

### 3.4 删宿主

| 用例 | 应得 | 现状 |
| --- | --- | --- |
| 删仍有子空间的节点 | 「下面还有空间」，还在 | 有。验收 7 |
| 删仍有**直接**资产的节点 | 「这里还有资产」 | 有 |
| 机柜上有服务器、服务器上有硬盘 | 因服务器是直接资产而拒绝；硬盘不计入机柜直接资产 | 设计 §5 有。无独立验收 |
| 删挂着硬盘的服务器 | 「请先移出硬盘」，两条都在 | 有。验收 14 |
| 先把硬盘改到仓库，再删服务器 | 应成功 | 未写，逻辑上成立，应补验收 |
| 确认值不是 `yes` | 「请确认删除」 | 有 |
| 数据库 RESTRICT 挡第二层 | 设计 §11 | 未规定 `IntegrityError` 必须译成上述中文，禁止 500 |
| 删硬盘 | 应成功，服务器仍在 | 未写 |

服务器改到另一机柜空闲 U 后硬盘仍挂着、导出路径变新机柜：验收 14 有，成立。

### 3.5 设计未写死、实现会分叉的宿主组合

1. **空间外键和挂载外键同时有值**：违反「恰好一个宿主」。无提示、无验收。必须拒绝，建议「请只选择一种位置」。
2. **两个外键都空**：草案有「请选择位置」。有。
3. **把硬盘改成服务器、但仍挂在另一台服务器上**：服务器不能挂资产。设计 §7.2「类型修改后连同现有宿主一起重新校验」；草案 §5.3 只写了**服务器改成别的类型且仍挂硬盘**时「请先移出硬盘」。反向未写。
4. **仓库里的服务器提交了起始 U**：验收 10 有「这里不使用 U 位」。检查顺序第 2 步先做 U 范围、第 4 步才做宿主：没有机柜高度时第 2 步可能先报「U 位超出机柜」。提示会飘。必须规定：宿主不是机柜且 U 有值时，固定「这里不使用 U 位」，不再做范围计算。
5. **根为仓库的柜子放整机**：设计按「服务器可在仓库」扩展。原文「仓库」也可以只指仓库节点。见 §6 对设计自列风险的裁决。

## 4. 运维三问

对照 `delivery-ledger/docker-compose.yml`（卷字面量 `delivery_ledger_pgdata`）、`deploy/lib.sh`（`POSTGRES_DB=ledger`）、`发布构建标准.md` §1/§2/§4。

### 4.1 卷名与客户交付台账同名，是否可接受？

**不可接受。第 2 轮必须改成独立卷名，例如 `asset_ledger_pgdata`。在用户确认偏离原句之前，禁止写业务代码。**

原因不采信设计「字面值已拍板」：

1. Docker 显式 `name:` 的卷是**宿主机全局名**，不被 compose 项目名隔开。`delivery-ledger` 与 `asset-ledger` 两个项目会挂**同一数据目录**。
2. 两个 `postgres:16` 不能共写一份 PGDATA。后启动的实例会因锁文件失败，或在先停后起时直接打开对方的集群。
3. PostgreSQL 只在数据目录为空时消费 `POSTGRES_USER` / `POSTGRES_DB`。卷若已由交付台账初始化，本产品安装脚本写入 `.env` 的随机账号**不会**被创建；`DATABASE_URL` 指向 `asset_ledger` 时库往往不存在。现场看到的是连库失败，不是设计承诺的那句冲突日志。
4. 更坏的顺序：本产品先装、交付台账后起，交付台账会在同一卷上建自己的表。交付台账**没有**反向检查 `spaces`/`assets`。《发布构建标准》§4.1 要求该卷只承载交付台账业务库、升级不得换卷名。本产品去挂同一卷，就是去改写那份数据。
5. 设计把「同机同时挂载」写成测试挑战，但默认策略仍是同名。同机部署是两个内部工具的正常现场条件，不是边角。

用户原句里的卷名，来源是客户交付台账的运维硬约束，不是「两个产品必须共用一个卷」。对齐运维做法 = 每个产品**自己的**固定卷名、禁止 `down -v`、禁止改已装现场的卷名；不是把另一个产品的卷名抄过来。

若业务坚持不改字面（不推荐），最低补强仍必须全部满足，否则同样不通过：

- 《部署说明》写死：禁止与客户交付台账安装在同一 Docker 宿主机；
- `install.sh` 发现名为 `delivery_ledger_pgdata` 的卷已存在则退出，不得 `up`；
- compose **不得**把已有卷挂进本产品的 postgres。

即便如此，卸载交付台账但按标准保留卷之后，本产品仍会误挂。所以独立卷名才是可验收解。

### 4.2 库名隔离是否够？

**不够。库名 `asset_ledger` 对「两个独立 PostgreSQL 实例」有效，对「同名卷争用同一数据目录」无效。**

设计的启动检查：当前**连接库**里若有表 `deliveries` 则退出，日志「数据库卷与客户交付台账冲突」，不建 `assets`，不写 `schema_migration`（设计 §8、草案 §2.1、验收 17）。

交付台账的业务表在数据库 `ledger` 里（`deploy/lib.sh` 的 `POSTGRES_DB=ledger`）。本产品 `DATABASE_URL` 连的是 `asset_ledger`。PostgreSQL 表是库内对象，连 `asset_ledger` **看不见** `ledger.deliveries`。因此：

- 同卷、不同库名：检查永远不触发；
- 同卷、同库、碰巧连上 `ledger`：才会看到 `deliveries`，但这已经不是设计写的连接方式；
- 空卷：检查通过，建本产品表。随后交付台账若也挂上该卷，两边的 `schema_migration`（同表名、都有 `0.1.0`）会互相污染。

结论：库名隔离是必要的，但只在**卷名也隔离**时成立。`deliveries` 检查不能当卷隔离的替代。卷改名之后，这条检查可降为防御误配 `DATABASE_URL` 的附加项，仍建议保留，并改成：连上后若存在 `deliveries` **或** 已存在非本产品的业务库/表，则退出。不要改成「看见任何陌生表都退出」（设计 §13 最后一行这点成立，后续自己加表会被误杀）。

另：postgres **不得**映射宿主机端口。两套产品若都发 5432，即使卷已分开也会抢端口。设计未写。

### 4.3 离线包是否写清？

**部分。架构条款够用来否决错架构；发布包形态不够用来打出可安装的包。**

已写清、且与《发布构建标准》§2 对齐的：

- 产物 `dist/asset-ledger-<版本>.tar.gz`
- 包内镜像只有 `asset-ledger:<版本>` 和 `postgres:16`
- 二者 Architecture=amd64，且 `docker run --platform linux/amd64 … uname -m` 为 `x86_64`
- Apple Silicon 必须压扁，禁止把 arm64 内容标成 amd64
- `pull_policy: never`；运行机只 load + compose up；可无 DNS、不访问 `registry-1.docker.io`
- 升级保留 `.env`、`backups/` 和卷；禁止 `compose down -v`；升级前备份；`/healthz` 为完成判据

未写清、实现轮会漏的（对照交付台账 `deploy/package.sh`、`Dockerfile`、发布构建标准 §2.1）：

| 缺口 | 为何必须写进本产品《发布构建标准》草案 |
| --- | --- |
| 目录树无 `vendor/wheels/`、无 `images/` | 设计 §11 的树只有 `deploy/*.sh`。没有 manylinux x86_64 wheel，构建阶段会访问 PyPI；运行机无网。 |
| 包内文件清单 | 交付台账要求 `VERSION`、`images/*-amd64.tar.gz`、`deploy/`、`部署说明.md`、发布构建标准；禁止带现场 `.env` 和业务数据。本设计只点了 tar.gz 和两镜像。 |
| 基础镜像与镜像站 | 交付台账默认 `docker.m.daocloud.io/library` + `python:3.12-slim`。本设计未钉 Python 镜像。 |
| 压扁步骤 | 只说「构建后的压扁」，未要求 create+commit（或等价）后再 inspect。仅 `docker pull --platform` 不够，交付台账标准写过。 |
| postgres 不映射宿主机端口 | 「仅 compose 内 postgres:16」的可验收句子。 |
| 运行机禁止 `compose build` / `pull` | 草案 §2 有 load，未写禁止项。 |
| `install.sh` 拒绝已有安装目录 | 交付台账硬禁止用安装脚本覆盖已装现场。 |
| 备份内容 | 至少 `db.sql` + `VERSION`。本版无附件目录，不要抄 `files.tar.gz` 当必选项。 |
| pytest 不得指向现场卷 | 交付台账 AGENT 提示词有。本设计只说 pytest 连 `DATABASE_URL`。 |

「打包对齐客户交付台账的架构条款，产品名换成资产台账」不能当省略号。实现轮要写的是本产品自己的两份文档，第 2 轮设计必须把上表写成可粘贴的条文，而不是转引。

## 5. 矛盾与漏洞

严重 = 不改会丢数、矩阵被打破、或验收自相矛盾；中 = 不改则实现分叉或现场不可用；低 = 应补但不挡主路径。

### 5.1 设计方已列风险：测试裁决

| 设计 §13 风险 | 裁决 | 级别 |
| --- | --- | --- |
| 卷名与交付台账相同 | **撞倒。** 见 §4.1。不能把「测试去撞」当成可以开工。 | 严重 |
| 办公空间拆成办公区/柜子/工位 | **不撞倒。** 用户点名了柜子和工位，「等空间」需要容器类型；硬盘三类都能放，覆盖「硬盘在办公空间」。空库必须先建办公区才能建工位，写进空态文案即可。不要合并成单一「办公空间」类型。 | — |
| 仓库下的柜子可以放服务器 | **建议收紧，不强制。** 原文「服务器可能在机柜或仓库」未提到柜子。整机进储物柜能讲成「在库、不占 U」，但和「柜子」日常含义冲突。第 2 轮必须**二选一写死**：要么保持并可测，要么柜子一律只放硬盘。禁止编码时再猜。 | 中 |
| 机房下面不能建柜子 | **产品缺口，须终裁。** 实现做得到（加一格矩阵），不是技术限制。若本版坚持机房只出机柜，要在《功能说明》用正向句写「机房内备件放入仓库」，并加验收：机房下创建柜子提示「这里不能放柜子」。 | 中 |
| 路径最多 4 层 | **规则可接受，移动实现不可接受。** 五层园区会被拦，设计已说明。创建侧可测。移动侧必须改成检查整棵子孙，见 §2.4。 | 严重（移动） |

| 无在用/报废/借出；删除即物理删除 | **可留，但备份必须可执行。** 误删只能靠升级/手动备份。`backup.sh`/`restore.sh` 不能只出现在目录树。 | 中 |
| 机柜只读整宽正面 | **可留。** 与交付台账拖拽不同，不是本产品范围。半 U/背面互相重叠是预期。 | 低 |
| 槽位是位置备注、不校验占用 | **可留。** 两块盘可写同一槽位。不要在实现里半套唯一槽位。 | 低 |
| 型号自由文本 | **可留。** | 低 |
| 本版只有导出 | **可留。** 符合原文。 | — |
| 无登录 | **可留。** 与交付台账本版一致。端口暴露即能改删，部署说明写清可信内网。 | 低 |

### 5.2 新发现问题

1. **（严重）`deliveries` 检查与库名 `asset_ledger` 互斥。** 检查的是当前连接库的表；交付台账的 `deliveries` 在 `ledger`。按设计自己的连接方式，验收 17 在真实同卷场景下**测不绿**（连不上或连到空库），起不到保护卷的作用。app 若因检查 `sys.exit`，compose `restart: unless-stopped` 会空转；postgres 已经挂上对方数据目录。检查点放在应用层、发生在 postgres 入卷之后，顺序就错了。
2. **（严重）移动空间不检查子孙深度。** 见 §2.4。合法 UI 操作即可制造第 5 层。
3. **（严重）两份「同一套规则」并不相同。** 设计开篇声称与草案同一套。至少这些对不齐，实现会选边：
   - 设计 §6「缺省提交时拒绝」占用高度 vs 草案 §5.2「清空后提交才拒绝」
   - 设计 §5 超层那句 vs 草案验收 4
   - 资产名称是否去首尾空白：草案 §6 要去，设计 §7.2 只写 1–200 字
   - 服务器仍挂硬盘时改类型：只在草案 §5.3
   - 「请填写机柜高度」「MAC 格式不正确」「说明过长」「名称过长」等提示只在草案
   - 设计验收 6 无非法父级的提示原文
4. **（中）同时填写 `location_space_id` 与 `mounted_on_asset_id` 未定义。** 「恰好一个」没有失败提示。
5. **（中）U 校验与宿主校验顺序。** 非机柜带 U 可能先打出「U 位超出机柜」。
6. **（中）U 重叠只有应用层检查。** 并发两次 POST 可双写重叠 U。本版若不用排他约束，必须 `SELECT … FOR UPDATE` 该机柜资产行，并写进规格。
7. **（中）FK RESTRICT 与提示语。** 未规定完整性错误转中文。测试直打删除接口时可能 500。
8. **（中）离线目录与 Python 3.12 / wheels 未钉。** 见 §4.3。SLES 运行机无编译器、无 DNS，漏 wheel 就是装不上。
9. **（中）postgres 端口、pytest 禁指现场卷、install 拒绝覆盖，均未写。**
10. **（中）硬盘网络字段 vs 用户清单。** 要在规格里正向写「硬盘不记录 BMC/业务 IP/MAC」，避免实现按「四种资产同一张表单」放开。
11. **（低）编辑提交相同类型是否算改类型。** 见 §2.3。
12. **（低）导出 `Content-Disposition` 中文文件名未规定。** `资产台账.xlsx` 在部分浏览器会乱码。
13. **（低）占用高度 0/非整数无提示原文。**
14. **（低）首页「硬盘数」是否含挂在服务器上的硬盘。** 未定义。按类型计数则应含。

## 6. 第 2 轮强制修订清单

### 必须改（不改不得编码）

1. **卷名改为独立名字**（建议 `asset_ledger_pgdata`），升级/备份/恢复都只用新名字。在设计 §2/§11、草案 §2、compose YAML 示例、验收句同步改。写明：不挂、不改、不删客户交付台账的 `delivery_ledger_pgdata`。若用户书面坚持原名，改为「禁止同机」+ 安装前发现该卷已存在则失败、postgres 不得入卷；仍须说明误挂会损坏交付台账。默认路径是改名。
2. **启动检查改到「连得上的那个集群」上可观测的事实**，或在改卷名后降级为误配防护。禁止再把「当前库有 `deliveries`」写成能防止同名卷的主方案。验收 17 按新策略重写：同机已装交付台账时，本产品要么根本挂不上那卷，要么明确失败且**交付台账表和卷内容不变**。
3. **移动空间：整棵子孙新深度都必须 ≤ 4**，失败提示「空间层级过深」，父级不变。补验收：把深度 4 的树移到另一根办公区下，拒绝。
4. **防环验收补「父级设为自己」。** 提示仍用「不能放到自己的下级」。
5. **消除设计与草案冲突**：占用高度预填/清空、超层那句、资产名称去空白、改类型+仍有硬盘、非法父级提示原文。贴《功能说明》时只留一份。
6. **宿主二选一**：两个外键都有值时拒绝并给提示；写入验收。
7. **非机柜位置只要 U 有值，固定提示「这里不使用 U 位」**，不要先按机柜范围报错。
8. **离线发布写成可粘贴条文**（本产品自己的《发布构建标准》草案，允许先放在 `docs/`）：Python 3.12；`vendor/wheels` manylinux x86_64；包内 `images/` + 两镜像压扁校验；基础镜像/镜像站；禁止运行机 build/pull；postgres 不映射宿主机端口；不占用宿主机原有 PostgreSQL；`install.sh` 拒绝已有安装目录；备份至少 `db.sql` 与 `VERSION`；pytest 的 `DATABASE_URL` 不得指向现场卷。
9. **仓库柜子是否允许服务器/交换机/防火墙：二选一写死**，并改第 6 节表与验收 8。
10. **机房下柜子：二选一写死**（允许并改矩阵，或明确「机房内备件放入仓库」+ 验收拒绝句）。不要再写「若测试认为…」。

### 建议改

1. 类型编辑：仅当新类型 ≠ 旧类型时拒绝。
2. U 重叠：事务内锁定该机柜，或加排他约束。
3. `IntegrityError` → 已有中文提示，不得 500。
4. 补验收：相邻 U 可保存；端点重合算重叠；先移硬盘再删服务器；硬盘进机房；机柜改到根；四层办公区下再加工位失败。
5. 导出文件名的 `Content-Disposition`（UTF-8 filename*）。
6. 占用高度 0/非整数的提示原文。
7. 首页硬盘数 = 类型为硬盘的资产数（含挂在服务器上的）。
8. 检查顺序写明矩阵 vs 防环 vs 深度的先后，一次只返回第一句。
9. 一块 MAC 的产品说明写在页面字段旁，避免现场以为还能填 BMC MAC。
10. 物理删除的风险写进《部署说明》：删前备份。
